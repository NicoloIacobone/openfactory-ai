- **Context:** the project brief suggests Jazzy on Ubuntu 24.04 but allows any working distro.

- **Evidence:** audit 2026-10-28 (`docs/environment.md`): `ros2 doctor` passes, pub/sub works, Gazebo Harmonic, MoveIt 2 and UR packages are available as aarch64 binaries.

## D-004 — Robot arm

- **Context:** the brief suggests a mature arm such as UR5e or Franka Panda.
- **Decision:** UR5e, from the Jazzy apt packages (`ur_description`, `ur_simulation_gz`, `ur_moveit_config`); Franka has no Jazzy apt package here.

## D-005 — Gazebo Harmonic with the Ogre 1 render engine, sensors on the VM display

- **Context:** the VM GPU is virtio (`virgl`) and exposes only OpenGL 2.1, no core profile. Gazebo Harmonic renders cameras with `ogre2` by default, which needs OpenGL 3.3+.
- **Decision:** Gazebo Harmonic (Sim 8.15, `ros-jazzy-ros-gz`) with `render_engine` set to `ogre` in the Sensors system and `--render-engine ogre` for the GUI. Any simulation with camera sensors runs with `DISPLAY` set to the VM graphical session (Xwayland `:0`); `--headless-rendering` is not usable. Physics-only runs can stay fully headless (`gz sim -s`).
- **Evidence:** probe 2026-10-28 (`docs/environment.md`, "Rendering probe"): `ogre2` segfaults with EGL headless, with EGL + `LIBGL_ALWAYS_SOFTWARE=1` and through Xwayland (Ogre-Next always selects the EGL hardware device, so llvmpipe's OpenGL 4.5 is never used); `ogre` through Xwayland publishes RGB and depth with correct values.
- **Consequences:** Ogre 1 is the older engine (simpler lighting, fewer features); third-party worlds that hardcode `ogre2` (e.g. the UR Gazebo launch, phase 1) must be overridden. Revisit if the VM gets a GPU with OpenGL 3.3+.
- **Status:** accepted for sensors and for the GUI (`gz sim --render-engine ogre` on the VM desktop, verified 2026-10-29).

## D-006 — Cell table from one layout file; standard joint trajectory controller

- **Context:** phase 1 needs the table in Gazebo (physics), TF and the MoveIt collision world. Links of one Gazebo model do not collide with each other, so a table inside the robot model would not stop the arm physically. The vendor simulation uses `ur_controllers/ScaledJointTrajectoryController`, which only makes sense with the real robot's speed scaling.
- **Decision:** table size/pose and robot mount live in `openfactory_description/config/cell.yaml`. The same xacro produces the robot + table URDF for `robot_state_publisher` and MoveIt, and the robot-only URDF spawned in Gazebo next to a separate static table model built from the same macro. A pytest checks both against `cell.yaml`. Arm motion uses the standard `joint_trajectory_controller`; MoveIt loads only the OMPL pipeline.
- **Consequences:** MoveIt sees the table as a robot link (allowed collisions with `base_link_inertia` and `shoulder_link` in the SRDF), not as a planning-scene collision object. Bins and camera mount (phases 2–3) are revisited when a scene node exists. The URDF given to MoveIt differs from the RSP one only in the Gazebo controllers path.
- **Evidence:** 2026-10-29 cell launch (`docs/environment.md`): TF matches `cell.yaml`, MoveIt rejects arm–table contact, RViz Plan & Execute runs through `joint_trajectory_controller`.
- **Status:** accepted.
- **Update 2026-11-13:** the bins (D-008) and the camera body (D-011) became fixture links like the table; the planning-scene world holds objects only.

## D-007 — Simple parallel-jaw gripper, friction grasp

- **Context:** phase 2 needs a gripper for cubes, cylinders and prisms of about 5 cm. `ros-jazzy-robotiq-description` exists in apt, but the 2F-85 needs an install, has a mimic linkage, and friction grasps with it in Gazebo are known to be fragile; the VM has 3.8 GB RAM.
- **Decision:** a project-defined gripper in `openfactory_description` (`urdf/gripper.xacro`, sizes in `config/gripper.yaml`): box palm on `tool0`, two prismatic box fingers along `tool0` y, opening 0–0.085 m, `right_finger_joint` mimics `left_finger_joint`, TCP frame `gripper_tcp`. Driven by `position_controllers/GripperActionController` (`gripper_controllers`, already installed) in its own `ros2_control` block of `gz_ros2_control`. Objects are held by friction only: no attach plugin, no `DetachableJoint`. If friction grasps prove unreliable, friction, effort, speed and object mass are tuned first; any attach mechanism needs the user's approval and a new entry (it bends rule 1).
- **Evidence:** VM check 2026-11-10: `gripper_controllers` 4.42.1 registers `position_controllers/` and `effort_controllers/GripperActionController`; `gz_ros2_control` 1.2.20 loads every `ros2_control` block and drives URDF mimic joints listed without command interfaces (upstream `component_parser.cpp`, `gz_system.cpp`). Position commands become joint velocity commands in Gazebo.
- **Gazebo joint limits (2026-11-10):** a Gazebo joint driven onto a position limit or onto its velocity limit stops following `gz_ros2_control` commands (cf. gz_ros2_control#165/#192). First runs: with the initial state on the stroke limit the fingers never moved; with a 0.1 m/s velocity limit a finger moving in the direction of gravity ran on to its end stop and stuck. Fix: joint limits are the commanded stroke ± `limit_margin` (5 mm), and the velocity limit (10 m/s) stays above every command `gz_ros2_control` issues (finger 0.1 × 500 Hz × error, mimic finger 500 Hz × lag). Finger speed is then set by the plugin's position gain, not by the URDF limit. Check: close, open, 0.02, close, open, all `reached_goal`, both fingers within 0.2 mm of each other, no drift to the end stops.
- **Consequences:** no vendor gripper mesh or driver; a Robotiq can replace it later behind the same `GripperCommand` action. MoveIt has a `gripper` group and end effector but does not plan the fingers.
- **Status:** accepted (E-002: 30/30 friction grasps, no slip).

## D-008 — Bins and floor as fixture links, like the table

- **Context:** phase 2 needs an input and a destination bin in Gazebo (physics), TF and the MoveIt collision world, and the floor in MoveIt (the gripper extends the arm's reach below the table top). D-006 left open whether fixtures beyond the table become planning-scene objects published by a node.
- **Decision:** extend D-006. Bin layout (centre on the table, inner size, wall thickness) lives in `cell.yaml`; `urdf/bin.xacro` builds an open-top bin (floor + four walls in one link, frame at the inner floor centre). Gazebo spawns table + bins as one model fixed to the world (`fixtures.urdf.xacro`, replacing `table.urdf.xacro`); the cell URDF adds the same links plus a collision-only `floor` box when `include_fixtures:=true` (renamed from `include_table`). Fixture pairs that touch or never move relative to each other have collisions disabled in the SRDF; arm and gripper links never do. The planning scene stays reserved for objects (known pose in phase 2, perceived from phase 3).
- **Evidence:** pytest checks both URDF variants against `cell.yaml` (bin pose, outer envelope, free inner volume, bins inside the table top and apart). Cell launch 2026-11-10: TF `world → input_bin` (0.40, −0.30, 0.76), `world → output_bin` (0.40, 0.30, 0.76); with the gripper pointing down and `gripper_tcp` 4 cm above each bin floor, MoveIt finds a collision-free IK solution at the bin centre and none above a wall (forced solutions there collide `gripper_palm`/fingers with the bin).
- **Consequences:** moving a bin means editing `cell.yaml` and restarting the cell; no runtime reconfiguration, which the MVP does not need.
- **Status:** accepted.

## D-009 — Object catalog, known-pose input, ground truth outside ROS

- **Context:** phase 2 picks objects at a known pose before any perception exists, and needs the simulator's object poses to judge success without letting them reach perception or manipulation (rule 5).
- **Decision:**
  - One object catalog (`openfactory_description/config/objects.yaml`); Gazebo models are generated from it (`scripts/scene_objects.py`, pytest), so geometry has a single source.
  - Phase 2 object poses come from a versioned trial config and are given to manipulation as fixed infrastructure input, documented as such; the harness spawns the object at that pose before the cycle. This is the known-pose baseline, not perception.
  - The harness spawns, removes and observes objects through Gazebo Transport (`scripts/gz_scene.py`). Ground truth is read from `/world/cell/dynamic_pose/info` by the harness's evaluation code only and is not bridged to ROS.
- **Evidence:** VM check 2026-11-10: bridging `Pose_V` to `tf2_msgs/TFMessage` drops the entity names (empty `frame_id`/`child_frame_id`), so a ROS topic would need an extra relay node; the Gazebo message carries the names. Cube, cylinder and prism spawned in the input bin rest at the expected heights (0.785, 0.800, 0.7816 m) with 0.00 mm drift in 5 s; a prism spawned standing on its triangular face rests with its origin at 0.790 m, confirming the extruded polyline is centred on the object frame; `create/blocking` and `remove/blocking` succeed.
- **Consequences:** ground truth is not visible in RViz; trial logs carry the evaluated poses instead. CLAUDE.md rule 5 still holds: no ROS ground-truth topic exists, and any future one lives under `/ground_truth/`.
- **Status:** accepted for phase 2.

## D-010 — Phase 2 motion strategy: separate plan/execute, straight lines near objects

- **Context:** the deterministic pick-and-place cycle must be collision-aware (rule 4), split planning and execution time (E-001 note), and hold objects that are gripped by friction only (D-007).
- **Decision:**
  - Free-space moves (ready, pre-grasp, back to ready) are OMPL plans through `/move_action` with `plan_only`, executed separately through `/execute_trajectory`.
  - Every move near or with an object is a collision-checked straight `tool0` line from `/compute_cartesian_path` (approach, lift, transfer at lift height, descend, retreat) and must be ≥ 99 % feasible. The transfer is a line, not a free plan, so the tool stays vertical: in the first trial a free-space transfer let the cube pivot out between the pads (`grasp_slipped` after transfer).
  - The object enters the planning scene at its known pose (raised 2 mm so it does not touch the bin floor), is attached to `gripper_tcp` by id with the gripper links as touch links, and is detached and removed after release. Attaching by id already moves the object out of the world; removing it in the same diff makes the whole request fail.
  - Grasp evidence: the jaw opening (left + right finger) must stay within 4 mm of the object width after closing (`grasp_failed`) and after lift and transfer (`grasp_slipped`). One finger alone is not evidence: while holding, the commanded finger reaches its close target and the mimic finger yields, so the object shifts about 5 mm toward one pad with the same squeeze. A left-finger-only check flagged held objects as slipped and the recovery then dropped them (first harness smoke run).
  - On a failure the cycle stops and recovers: open, clear the scene object, straight rise, joint move to ready. A free plan out of a bin is rejected by MoveIt's ValidateSolution (fingers graze the walls between OMPL's checked states).
- **Evidence:** `pick_place_once` 2026-11-10 in the running cell: cube, cylinder and prism each picked and placed at the first attempt (20.0, 20.8, 25.1 s, planning ≈ 0.3 s of it); empty-bin cycle ends in `grasp_failed` at `close` and recovers to ready.
- **Consequences:** the straight transfer assumes bins reachable along a line at lift height, true for this cell; later phases with arbitrary placements may need orientation path constraints instead. Objects land about 1 cm off the place point along the finger axis (release pushes them); the closing test measures it.
- **Status:** accepted for phase 2.

## D-011 — Fixed overhead RGB-D camera modelled on the RealSense D415, with a simple depth error model

- **Context:** phase 3 needs one fixed RGB-D camera whose pose appears once in the description, TF and MoveIt, light enough for the 3.8 GB VM, with data that are not unrealistically clean. Camera parameters come from the D415 datasheet (Intel 337029-017, September 2023), read for the `synthetic-rgbd-manufacturing-perception` project.
- **Decision:**
  - Geometry of a D415 depth mode: 640 × 360 at 5 Hz, depth FOV H 65° (square pixels give V 39.4°; the datasheet's 71° is the FOV of the infrared imagers, which matters when simulating the stereo pair, not its output), Min-Z 0.24 m at this resolution, valid up to 2 m (range of the datasheet KPIs), baseline 55 mm, body 99 × 23 × 20 mm. One optical centre for colour and depth.
  - Mount: fixed, straight above the centre of the input bin, optical axis vertical, 0.70 m above the bin floor (world z 1.46 m): about 1.4 mm per pixel on the floor, the whole bin and its rim in view, the walls never hide the floor, every catalog object beyond Min-Z. Pose in `cell.yaml` (`camera_mount`), sensor in `config/camera.yaml`, macro `urdf/camera.xacro`: the body is a fixture link like the bins (D-008), a collision obstacle for MoveIt and Gazebo; the support (ceiling bracket) is not modelled.
  - The Gazebo `rgbd_camera` is a `<gazebo reference>` block of the macro, emitted only for the fixtures model. Messages carry `camera_optical_frame` through `gz_frame_id`. Image and depth are bridged lazily (rendered only while a ROS node subscribes); `camera:=false` drops the sensor for runs without a display (D-005).
  - Depth error model in a separate node (`openfactory_simulation/depth_sensor_model`), between the bridge and perception: Gaussian noise of 0.08 px on the disparity f B / z (σ_z = 1.4 mm at 0.70 m, 2.9 mm at 1 m), rounding to the 1 mm depth unit, NaN outside [Min-Z, 2 m]. Noise is seeded per frame from (seed, image stamp). The closing test runs with the model on.
- **Evidence:** E-003 part A (2026-11-11): `camera_info` equals the pinhole model of `camera.yaml`; the bin floor seen by the camera is the plane z = 0 of `input_bin` within 0.0001 mm and 0.0002°; a known point reprojects within 0.2 px; the measured depth noise on the floor is 1.452 mm against 1.448 mm from the model. URDF-to-SDF conversion keeps the sensor on the lumped `table` link at the mount pose; `gz sdf` only warns that `gz_frame_id` is not in the SDF schema. Cell with camera, depth model and perception: real-time factor 1.0, 1.5 GiB used.
- **Calibration finding:** Gazebo reports the principal point as (width / 2, height / 2) while pixel (u, v) looks along the ray of (u + 0.5, v + 0.5), half a pixel off the convention of integer pixel centres (0.7 mm on the bin floor). Perception adds a measured correction of (−0.5, −0.5) px to the `camera_info` principal point (`perception.yaml`); K itself is never hard-coded.
- **Limits:** the depth error is independent per pixel. It is not a stereo-matching simulation: no spatially correlated error, no holes on shiny or textureless surfaces, no flying pixels at depth edges, no invalid band at the left image border, no Min-Z from a disparity search range. The `synthetic-rgbd-manufacturing-perception` experiment found that such a noise-on-ideal-depth model is optimistic compared with simulated stereo matching, strongly so on metal; the catalog objects here are matte. Ogre 1 renders flat-shaded colour (D-005), so colour is used for debug views only. Delivered frame rate is 3.6–4.2 Hz, below the nominal 5 Hz.
- **Status:** accepted for phase 3.

## D-012 — Geometric perception baseline: top-view height map and model-based primitive recognition

- **Context:** phase 3 needs object hypotheses (class, pose, confidence) from camera data and TF only, cheap enough for the VM, as the baseline any learned perception is later compared with (rule 3).
- **Decision:**
  - NumPy and OpenCV only, both already installed; Open3D is not needed (the pip check deferred since phase 0 is dropped). Pure functions in `openfactory_perception/core`, a thin node around them.
  - Pipeline per depth frame: depth → points in the optical frame with K from `camera_info` (NaN, inf, 0 and out-of-range pixels rejected) → `input_bin` frame through TF at the image stamp → crop to the inner bin volume (5 mm from the walls, below 0.12 m) and remove the floor as the known plane z = 0 with a 6 mm threshold (about 4 σ of the depth noise) → mean-height map on a 2 mm top-view grid, which is also the downsampling → morphological closing and opening, connected components, blobs under 3 cm² dropped → per blob: top-layer height, minimum-area footprint rectangle, filled share of the rectangle, share of the footprint at top height.
  - Recognition is model-based: each catalog shape (`objects.yaml`, fixed infrastructure) predicts those features, including the effect of the floor threshold on the prism's slanted faces; the class is the shape with the smallest normalised residual and the confidence is exp(−residual / 2). Below 0.2 the cluster is published as `unknown`, never dropped silently. Pose: footprint centre, catalog height / 2, yaw from the footprint's long axis reduced by the shape's symmetry (cube 90°, prism 180°, cylinder none).
  - Output: `vision_msgs/Detection3DArray` in `world`, one per depth frame, stamped with the image stamp (`docs/architecture.md`). Colour is not used for recognition.
- **Scope:** separate objects resting in their catalog orientation. Touching or stacked objects, tumbled objects, and anything in the bin volume that is not a catalog object (the arm during a pick) are phase 4.
- **Evidence:** 63 pytest cases on synthetic z-buffered views of the catalog objects (each step, and the whole pipeline with and without the depth model); synthetic Monte Carlo before the first live run: 1800 random single-object views, 0 wrong classes, position error at most 1.1 mm, yaw at most 2.1°, 0 detections in 200 noisy empty bins, 9 ms per frame. Live: E-003 part B.
- **Status:** accepted for phase 3.
- **Update 2026-11-13:** the scope line above did not happen as written. Phase 4 kept separate objects in their catalog orientation and kept the arm out of the views by looking only from ready (D-017); tumbled objects came in phase 5 as `unknown` clusters (D-018); touching and stacked objects are still out of scope.

## D-013 — Camera-driven pick: the most confident hypothesis replaces the known pose

- **Context:** phase 3 must show the perception output driving a pick, without anticipating the grasp selection and recovery of phase 4.
- **Decision:** `openfactory_manipulation.camera_pick.perceive` moves the arm to the ready configuration (clear of the input bin), waits 0.5 s, takes the first `/perception/objects` message stamped after that, and selects the hypothesis with the highest confidence among catalog classes at or above 0.5. Its class and its pose, expressed in `input_bin`, are the input of the unchanged `PickPlace.run` cycle (D-010), which also places the object in the planning scene. The object rests on the bin floor, so its height comes from the catalog. `PickPlace.run` records the pose source (`known_pose` or `perception`) in its result (`object_pose`, formerly `known_pose`). No hypothesis ends the attempt as `no_detection`.
- **Consequences:** one grasp per object and no feasibility search: the closing test draws object centres from the middle of the bin (±75 mm × ±35 mm), where the palm, which goes below the bin rim, clears the walls for any yaw. Phase 4 replaces the selection with grasp candidates and hard feasibility filters and widens the region.
- **Evidence:** E-003 part C.
- **Status:** accepted for phase 3.

## D-014 — Gripper fingers longer than the bin walls

- **Context:** with the 60 mm fingers of D-007 the palm (120 × 60 mm) went below the rim of the 100 mm bin walls at every grasp, so an object could only be picked if its centre was about 60 mm from the walls along the finger axis and 30 mm across it. D-013 worked around it by drawing objects in the middle of the bin (±75 × ±35 mm). Phase 4 picks objects anywhere in the bin.
- **Decision:** fingers 110 mm long (`gripper.yaml`: `finger.size[2]` 0.06 → 0.11, `tcp_offset` 0.085 → 0.135, so `gripper_tcp` stays 15 mm above the fingertips). With the fingertips 5 mm above a bin floor the palm is 115 mm above it, 15 mm over the rim: only the fingers (20 × 10 mm each) enter a bin. Everything else of D-007 is unchanged: stroke, joint limits and margins, effort, friction grasp, no attach mechanism. `ready_joints` is unchanged (`gripper_tcp` now 0.24 m above the bin floors).
- **Evidence:** pytest in `openfactory_description` (the fingers are longer than any bin wall is high) and in `openfactory_manipulation` (`test_grasps.py`: a cube 5 mm from a wall has a feasible grasp along the wall with these fingers and none with the short ones). Live, 2026-11-11, same cycle and configs as E-002 and E-003: `phase2_pick_place_20261111T130001Z_s1` 3/3 (one per type), 0 of 570 executed states in collision, place error mean 10.2 mm, max 17.5 mm (E-002: 9.9 / 17.5); `phase3_camera_pick_20261111T130115Z_s1` 6/6 (two per type), 0 of 1126 states in collision, cycle 17.7–18.8 s (E-003: median 18.4 s). The fingers open, pre-close, close and release in every cycle, so the joint-limit trap of D-007 did not come back.
- **Consequences:** `tool0` works 50 mm higher for the same grasp. The numbers of E-002 and E-003 were measured with the short fingers; the smoke runs above show the same behaviour, not a re-run of those tests.
- **Status:** accepted (user's choice for phase 4, 2026-11-11).

## D-015 — A held prism can turn between the pads: measured, grasp height kept

- **Context:** E-003 part C lost 2 of 10 prisms that ended in the output bin on another rectangular face: the prism turns about the finger axis while it is carried, and the jaw opening cannot see it. Phase 4 had to find the cause and a fix that keeps the friction grasp of D-007 (no attach mechanism).
- **Measurement:** `scripts/grasp_hold_probe.py` (config `scripts/config/phase4_hold_probe.yaml`, long fingers of D-014) runs the unchanged known-pose cycle of D-010 on a prism at 12 yaws, 15° apart, and samples its ground-truth pose every 0.2 s; the roll about the finger axis while the prism is in the air is compared between variants of `pick_place.yaml`. Runs of 2026-11-11: `phase4_hold_probe_20261111T162928Z_s1000` (five variants × 12), `…165106Z` (baseline × 24), `…165940Z` (ridge grasp × 24); 108 transfers.

| Variant | Transfers | Roll above 9° | Largest roll | Ended on another face |
|---|---|---|---|---|
| Baseline: TCP at the object centre, lines at 0.1 scaling | 36 | 5 | 114° | 1 |
| Lines at half speed (0.05) | 12 | 1 | 10° | 0 |
| Lines three times as fast (0.3) | 12 | 1 | 16° | 0 |
| Grasp 5 mm higher | 12 | 1 | 100° | 1 |
| Grasp 10 mm higher | 12 | 1 | 77° | 1 |
| Ridge grasp, 25 mm higher | 24 | 21 | 40° | 0 |

- **Findings:**
  - It is not a slip under acceleration. In every variant about one transfer in ten shows it, whatever the speed, and the roll appears as a jump between two samples during the transfer, after which the prism stays where it went. In the other transfers the roll is below 1°.
  - The size of the jump is that of a pendulum hanging from one lower corner of a pad. The pad is 20 mm wide, its lower edge 6.7 mm above the prism base in the baseline grasp; the centre of mass is 14.4 mm above the base. Hanging from a pad corner 10 mm off the centre line, the centre of mass comes to rest below it after 77° with the grasp 10 mm higher (measured 77°), 105° with 5 mm (measured 100°) and 128° at the baseline height (measured up to 114°). So the hold sometimes degenerates to one contact point per pad, which carries no torque about the finger axis; this is how the simulator builds contacts between the box pad and the triangular end face of the extruded mesh, not a lack of squeeze (20 N per finger, friction 1.0, object 0.1 kg).
  - Holding only the ridge, where the prism is narrower than the pads, bounds the swing (no pad corner touches the face) and never changed the face, but the prism then swings in nearly every transfer (median 24°).
  - No prism was dropped and none left the output bin: 108 of 108 deposited, and the jaw-opening checks passed in all of them.
- **Decision:** keep the grasp at the object centre and the line speeds of D-010. The hold is rigid in about nine transfers out of ten; one transfer in 60 at this height ended on another face (95 % Wilson interval 0.3–8.9 %), which the ridge grasp (0 of 24, interval 0–13.8 %) does not beat with the data at hand, while it makes the object swing every time. Raising the grasp by 5 or 10 mm is worse and is ruled out.
- **Consequences:** the goal set for this probe (no prism on another face in 30 transfers) is not met; it is a documented limit of the friction grasp on this shape in this simulator. With the phase 4 place criterion (D-017: at rest inside the output bin, on any face) it is not a failure, and E-004 reports how many deposited objects are not upright. The cell still cannot see the turn: the held object is hidden by the gripper from the only camera. Not tried: torsional friction or a different collision shape for the pads or the prism end faces; either needs a look at what the physics engine supports and a new entry.
- **Status:** accepted for phase 4.

## D-016 — Grasp selection: geometric top-down candidates, hard filters, baseline score

- **Context:** phase 3 picked one object with the single grasp of D-010 in the middle of the bin (D-013). Phase 4 picks among several objects anywhere in the bin, close to each other and to the walls, and needs the fixed order of the manipulation guide: generate, reject infeasible candidates with a reason, rank only the survivors (rule 4). This is also the baseline any learned ranking is compared with (rule 3).
- **Decision:**
  - Candidates (`openfactory_manipulation/core/grasps.py`, ROS-free): top-down grasps at the object centre, fingers closing across x and across y for a box, along 8 directions over 180° for a standing cylinder, across the length only for the prism (its triangular end faces; the slanted faces cannot be held by parallel pads). Grasp height from `grasp_offset` as in D-010.
  - The fingers approach and release pre-shaped to the object width plus `preclose_margin` per side instead of fully open, so that they fit between neighbours; the known-pose cycle of phases 2 and 3 keeps approaching fully open.
  - Hard filters, in this order. Geometric, in the same module: the object fits the open gripper (`gripper_width`); the two fingers and the palm, as top-view rectangles at their heights, keep `finger_clearance` (3 mm) from the bin walls (`wall_collision`) and from the footprints of the other objects in the view, unknown clusters included (`neighbour_collision`). Then MoveIt, which has the last word (`grasp_selector.py`): a collision-free IK solution 0.10 m above the grasp with the fingers at the approach opening, searched from the ready configuration (`ik_failed`); the straight approach line from that state (`approach_blocked`); the straight lift line (`lift_blocked`). All against the planning scene, which holds the fixtures and every object of the view.
  - Ranking of the survivors: `score = 1.0 · confidence + 0.5 · clearance / 30 mm − 0.3 · motion / 3 rad`, with the perception score of the object, the smallest gap of the gripper to walls and neighbours, and the largest joint displacement from ready to the validated pre-grasp. Weights in `pick_place.yaml` (`ranking`). Collisions never enter the score.
  - MoveIt filters run on the geometric survivors in order of a first guess of the score (motion unknown) and stop after `max_feasible` (4) feasible ones; the rest is logged as `not_evaluated`, not as rejected.
  - The move to the pre-grasp is a joint goal at the IK solution that was validated, so the approach line that is executed is the one that was checked.
- **Evidence:** 20 pytest cases in `test_grasps.py`. Development run `phase4_bin_picking_dev_20261111T172211Z_s1000` (seed 1000, 6 scenes of 5 objects): 29 picks, 315 candidates, rejections `wall_collision` and `neighbour_collision` only, no MoveIt rejection among those evaluated, 0 of 5228 executed states in collision, 0 objects disturbed. Evaluation: E-004.

## D-017 — Bin-picking loop: verify with the next view, place on a remembered grid, deposit criterion

- **Context:** the MVP needs the cell to empty a bin on its own, detect its failures and stop for a stated reason. There is one camera, above the input bin (user's choice for phase 4): the output bin is not observed, and the held object is hidden by the gripper.
- **Decision:**
  - Loop (`openfactory_manipulation/bin_picking.py`, state and rules in `core/task.py`): go to ready → view → all objects of the view into the planning scene → grasp selection (D-016) → pick and place → view. One view per pick: the view after a pick verifies it and is the input of the next one.
  - The cell counts a pick as done only if every stage and finger check of the cycle passed (D-010) **and** nothing is seen within 20 mm of where the object was (`object_not_removed` otherwise). It cannot see where the object ended.
  - Recovery and retries: after a failure the cycle recovers as in D-010, the cell looks again and selects again; a grasp that failed is not repeated (same place, same finger direction), an object is left alone after 2 failed grasps, a scene gets 2 attempts per object seen at its start and ends after 3 failures in a row. Scenes end with a reason: `bin_empty`, `no_feasible_grasp`, `only_unknown`, `output_full`, `attempt_budget`, `failure_budget`, `no_view`.
  - Place: a fixed grid of 6 points in the output bin (`pick_place.yaml`, `place.slots`), one object each, tried in order. Before anything moves, three lines are planned for a point from the lifted state: the transfer, the descent, and the retreat with the fingers open as after the release (they are closed on the object while it descends, and open they reach 5 mm further). A point that fails one of them is skipped. If no point is feasible the object is set down where it was picked (`place_blocked`) instead of being carried and dropped.
  - Memory of the output bin: a place point is taken as soon as an object left the input bin on its way there, also if the cycle then failed (an object lost over the output bin lies somewhere around that point). The cell keeps those objects as planning-scene obstacles, 8 mm larger on every side because an object shifts when the fingers let go (measured: median 4.5 mm). The grid leaves room for the fingers between two points in the worst orientation only up to about 10 mm of padding; a pytest checks it, and that the open fingers fit between every point and the walls.
  - Recovery never opens the fingers wider than the cycle does: fully open fingers push into whatever is beside them, and a finger pressed against a bin wall is a start state in collision from which MoveIt plans nothing.
  - Objects in the planning scene are beliefs, fixtures are not. If the arm cannot plan to ready (it is inside a bin, where a free plan grazes the walls, or it stands within the margin of a remembered object), the loop removes the objects from the scene, leaves straight up on a collision-checked line and goes to ready; the next step puts the objects back from the new view and from memory.
  - The planning-scene world belongs to the loop: it is emptied at every new scene, because `move_group` keeps the objects of a process that ended.
  - Evaluation criterion (harness, `scripts/bin_picking_eval.py`): an object is **deposited** when it is at rest inside the output bin volume, on any face. The upright criterion of E-002 and E-003 is reported, not required: the cell places objects next to each other with no view of the bin, and an equilateral prism rests the same way on each rectangular face (D-015). An attempt succeeds only if the cell reports it, ground truth shows its object deposited and no executed state is in collision.
- **Evidence:** 15 pytest cases in `test_task.py`, 18 in `tests/test_bin_picking_eval.py`. The first development run (`phase4_bin_picking_dev_20261111T171027Z_s1000`) showed why the world must be emptied: obstacles left in `move_group` by an earlier manual run blocked four of the six place points, so from the third pick on the descent was rejected and the recovery dropped the object (12 of 29 attempts counted). With the world emptied at reset and the put-back, `phase4_bin_picking_dev_20261111T172211Z_s1000`: 29 of 29 attempts, 29 of 30 objects deposited (28 upright), 5 of 6 scenes cleared and one ended as `no_feasible_grasp` with the object really left, 0 attempts on the empty bin, the cell's verdict and ground truth agree on every attempt. Evaluation: E-004.
- **Faults found by the evaluation runs and fixed** (each first run is reported in E-004):
  - `phase4_bin_picking_eval_20261111T173304Z_s1`: a cube slipped out of the fingers during a transfer (detected, `grasp_slipped`) and fell into the output bin; the next object was set down on it, its release stalled, the recovery opened the fingers fully into the bin wall and the arm could not be planned out any more. From there every scene ended as `no_view`: 52 of 100 objects.
  - `phase4_bin_picking_confirm_20261111T183107Z_s2`: three times the fingers, opening after a release, entered the 15 mm margin of a placed neighbour; the retreat could not be planned and the arm stayed in the bin for the following scenes: 73 of 100 objects. All three objects had been deposited.
- **Limits:** the cell does not know how an object lies in the output bin, nor where an object it lost ended. An object that shifts more than the padding when released (seen: up to 35 mm, once) can be touched by the fingers at the next place. Six place points: a scene with more objects ends as `output_full`.
- **Status:** accepted for phase 4.
- **Update 2026-11-13:** still how the single-arm cell works. In the ring of N arms every bin has a camera: place points and the arrival of the object come from the view of the destination bin (D-021).

## D-018 — Phase 5 scenes: tumbled objects, grasped as unknown clusters

- **Context:** phase 4 closed with 295 of 297 attempts successful (E-004). A learned grasp ranking needs failures to learn from and room to beat the baseline, and the recovery had met two failures only. Phase 5 needs a harder scene family on which the geometric model of D-012 and D-016 is incomplete, without anticipating piles, touching objects or new sensors.
- **Decision:**
  - Scenes (`scripts/config/phase5_tumbled.yaml`): as in E-004 (5 objects, separate, at least 8 mm from the walls and 10 mm from each other), but each cylinder lies on its side and each prism stands on a triangular end face with probability 0.5 (`tumbled_share`, `randomize_scene.sample_scene`). A cube looks the same on every face. The rest states are defined in `scripts/scene_objects.py` (`rest_rpy`, `resting_size`, `rest_error`); without `tumbled_share` the sampler draws nothing extra, so the scenes of phases 3 and 4 are unchanged (a pytest pins one).
  - Perception is unchanged: a tumbled object does not match any catalog model and is published as an `unknown` cluster with its footprint rectangle (long side along its yaw) and measured height. No new topic or field.
  - With `selection.unknown_grasps` the cell may try `unknown` clusters: two top-down candidates at the footprint centre, across the long and across the short side, with the TCP at half the measured height, through the same hard filters of D-016 (gripper width, walls and neighbours, then MoveIt IK and the approach and lift lines). In the planning scene and as a placed obstacle the cluster is the box of its footprint and height. A lying cylinder (80 mm long) only fits across its diameter; a standing prism fits both ways, one closing a face against the opposite edge, the other on two edges, which the baseline score cannot tell apart.
  - The jaw-opening checks compare with the measured width of a cluster, which is not a catalog size: the top view erodes sharp vertices (a standing prism measures 3–4 mm narrower than the jaws find it, and the first development run counted a held prism as `grasp_failed`). For `unknown` targets the tolerance is `selection.unknown_width_tolerance` (8 mm instead of 4); a miss closes the jaws 10 mm under the measured width (2 × `squeeze_depth`) and is still detected (pytest).
  - Nothing else of the loop changes (D-017): verification by the next view, budgets, place grid, recovery.
- **Findings in development (seed 5100):** lying cylinders measure 80 × 50 × 49 mm and are held across the diameter like the standing ones. A standing prism is the hard case. Across the short side the fingers close a face against the opposite edge and hold. Across the long side, with the TCP at the rectangle centre, the 20 mm pads do not reach the two base vertices and squeeze the slanted faces like a wedge: the prism slips out. The D-016 score prefers that side whenever it has more clearance.
- **Evidence:** E-005. With the baseline score: 195/200 objects and 195/212 attempts on the two held-out seeds, every failure a wedge, all detected and recovered; the phase 4 cell (`catalog_only`) deposits 128/200 on the same scenes.
- **Limits:** the footprint rectangle of a triangle is one of three equivalent ones, so a standing prism gets one face-against-edge candidate where three exist; when that one points at a wall the prism can be left (E-005 part C, `eval` scene 16). Touching, piled and tilted objects are still out of scope.
- **Status:** accepted for phase 5.

## D-019 — Learned grasp ranking: logistic P(success) on pre-motion features, compared on held-out seeds

- **Context:** the phase 5 goal is a learned ranking compared with the geometric baseline (rule 3, benchmarking guide: scoped AI that ranks; labels from simulated outcomes; batch training; no heavy training on the VM). The data are a few hundred attempts and the VM has numpy but no scikit-learn or torch (`docs/environment.md`); nothing is installed for this.
- **Decision:**
  - Strategies (`openfactory_manipulation/core/ranking.py`, `ranking.strategy` in `pick_place.yaml`): `baseline` (the D-016 score), `uniform_random` (a seeded uniform order of the feasible candidates, to collect outcomes without any score's preference) and `learned`. All three order only the candidates that passed every hard filter; MoveIt checks the survivors in the order of the strategy's score before motion is known, as in D-016.
  - Features of a candidate (`ranking.features`, one function for the log and for inference): one-hot class of the hypothesis (`unknown` included), perception score, grasp width and its ratio to the long side of the footprint (and that ratio again for `unknown` clusters only, so that a linear model can weigh the side a cluster is held across apart from the catalog shapes, whose ratio is fixed), height and height / width, clearance to walls and to neighbours (capped at 50 mm), position in the bin relative to its half sizes, finger direction relative to the bin, objects in the view, failed grasps already spent on this object. All from perception, geometry and the cell's own memory; nothing from the simulator.
  - Model: L2-regularised logistic regression on standardised features, fitted by Newton's method (`scripts/ranker_fit.py`, numpy); the L2 weight is chosen by 5-fold cross-validation with all attempts of a scene in one fold. The label of an attempt is its outcome as the harness judged it (`success`: the cell's verdict, the object deposited and no state in collision). Inference is a few lines of pure Python, so `openfactory_manipulation` gains no dependency. The model is a JSON file of weights, normalisation and provenance (runs, data hash, commit) in `openfactory_manipulation/config/grasp_ranker.json`.
  - Learned score: P(success) − `learned_motion` (0.1) × motion / `motion_cap`; the motion term breaks near-ties toward shorter moves.
  - Protocol (`scripts/config/phase5_tumbled.yaml`): training data from the `train` seed (5000) only, collected with `uniform_random`; development on seed 5100; code, thresholds and model frozen before the held-out seeds 51 (`eval`) and 52 (`confirm`), on which `baseline` and `learned` play the same scenes. `catalog_only` (the phase 4 cell, which never tries an `unknown` cluster) runs on the same scenes as a reference. `scripts/compare_strategies.py` reports rates with Wilson intervals and per-scene paired differences with a bootstrap over scenes. The learned ranking becomes the default only if its pick success is higher on both held-out seeds; otherwise the baseline stays and the result is reported as it is.
- **Evidence:** E-005 parts B and C. Trained on 320 attempts (33 failures) of the `train` seed: out-of-fold log-loss 0.065 against 0.332 for a constant, AUC 0.97. On the held-out seeds, pick success 99/101 and 99/102 against 100/109 and 95/103 for the baseline on the same scenes; paired difference over the 40 scenes +0.056 (bootstrap 95 % interval +0.022 to +0.092), failed attempts per scene −0.30 (−0.50 to −0.13); completion 199/200 against 195/200. Default since `5f1a5fa`: `unknown_grasps: true`, `ranking.strategy: learned`.
- **Limits:** the scene family has one failure mode that matters (the wedge of D-018); the model learned it from random-order outcomes without being told, but a hand rule written after seeing it would do as well. A ranking cannot refuse: when the wedge is the only feasible candidate it is tried. The model is linear and its L2 weight is the smallest of the grid. Training and evaluation share the scene family; other families are untested.
- **Status:** accepted for phase 5.

## D-020 — Ring of N arms: layout from the cell, one robot model, generated configuration

- **Context:** phase 6 asks for N arms passing objects round a loop, N chosen at launch, in the form the user gave it (2026-11-13): N arms and N bins, arm *i* picks from bin *i* and places into bin *(i + 1) mod N*; no conveyors yet (the first step of idea 1 in `docs/ideas.md`). Rule 4 needs every plan checked against the other arms; rule 7 forbids hiding an unreliable single cell under new complexity; the VM has 3.8 GiB.
- **Decision:**
  - **Layout.** Each arm keeps the local geometry measured on the cell in phases 1–5: its two bins 0.40 m in front of the base and 0.30 m to each side, the source on its right. Both numbers are read from `cell.yaml`, nothing is copied. The bins are then the vertices of a regular N-gon of side 0.60 m (`r_bin = chord / (2 sin(π/N))`) and the arms stand outside it on the axis of each side, facing the centre (`r_arm = chord / (2 tan(π/N)) + standoff`), on a round table. Pure Python with pytest (`openfactory_description/ring.py`). Arms inside the polygon were not considered further: they crowd the centre and put a lower bound on N.
  - **One robot model.** One URDF with every arm (prefix `arm_<i>_`), one `move_group` with one planning group per arm, one `controller_manager` with a trajectory and a gripper controller per arm, one `/joint_states`. A plan for one arm is checked against all the others because they are links of the same model; no second MoveIt instance, no relayed joint states. The alternative, one Gazebo model and one namespaced controller manager per arm, was kept as a fallback and not needed.
  - **Physical collisions.** Links of one Gazebo model do not collide with each other, so the ring model sets `self_collide`: arms must stop each other in the simulator too, or a planning fault would pass as a ghost crossing.
  - **Generated files.** xacro cannot loop and controllers, bridge, SRDF, kinematics and joint limits are per N: each launch writes them for its N to `/tmp/openfactory_ring/n<N>/`, from the cell's own files (one tuning for every arm, the cell's collision matrix for every arm). The generators are ROS-free modules with pytest. YAML is written without anchors: `rcl` refuses a parameter file with aliases ("Will not support aliasing"), which `yaml.safe_dump` emits for shared sub-objects.
  - **The cell is untouched.** Its launch, URDF, SRDF, interfaces and benchmarks stay; the shared xacro macros and the manipulation classes take the arm's names and bins as parameters whose defaults are the cell's.
- **Evidence:** VM, 2026-11-13, `ring_simulation.launch.py n:=2 camera:=false`: the five controllers active, real-time factor 1.00. Both arms sent towards each other through their trajectory controllers (no planner) stop at shoulder_lift −1.11 rad with "path tolerance violation"; the same goal for one arm is reached when the other is turned away and aborted when the other stands in its path: the arms collide physically. Closing the fingers on nothing still reaches the goal (pads 1.8 mm apart per finger). With MoveIt: `/check_state_validity` accepts every arm parked and one arm at ready, and rejects both arms at ready with contacts between `arm_0_gripper_palm`, `arm_1_gripper_palm` and the fingers. pytest: layout for N = 2 … 40 (every arm sees its bins as the cell's arm does, bases at least 0.60 m apart, everything on the table), URDF, controllers, bridge, SRDF against the URDF. E-006 for the loop itself.
- **Consequences:**
  - With N = 2 the cell's ready configuration puts both tools at the centre of the ring, between the two shared bins, so two arms cannot be at ready together. Arms that are not working are parked upright above their base (D-021).
  - Geometry sets no upper limit on N (neighbouring bases are `chord cos(π/N) + 2 standoff sin(π/N)` apart, never less than 0.60 m); the VM does (`docs/environment.md`).
  - The world origin of the ring is its centre, not the base of an arm.
- **Status:** accepted for phase 6.

## D-021 — Relay loop: one arm at a time, parked neighbours, place points and arrival from the view

- **Context:** the loop of D-020 runs for ever, so the destination bin of an arm is emptied by the next arm: the remembered place grid of D-017 cannot work. Every bin now has a camera. Several arms share one planning problem.
- **Decision:**
  - **One arm moves at a time** (user's choice, 2026-11-13). MoveIt plans an arm against the state of the others at planning time; that is a guarantee only if they do not move. Turns go round the ring (`core/relay.py`): the next arm whose source bin shows an object it may try and whose destination bin has a free place point; an arm with nothing to do is skipped.
  - **Parking.** Arms that are not working stand upright above their base (`relay.park_joints`): clear of every bin, of every camera view and of the working arm. A turn is park → ready → one bin-picking attempt → park.
  - **One camera and one perception per bin**, the cell's camera, calibration and node, in the namespace of the bin. Views are taken while every arm is parked or the working arm is at ready.
  - **Place points from the view.** A point of the cell's grid is free when every object seen in the destination bin is at least `place_margin` (45 mm) away, footprint circle to point; the roomiest point first. The objects seen there are planning-scene obstacles, grown by the cell's padding; the transfer, descent and retreat lines are checked as in D-017.
  - **A handover counts** when the pick is verified as in D-017 and the next view of the destination bin shows an object within `arrival_radius` (30 mm) of the place point. `arrival_radius` is smaller than `place_margin`, so an object that was already there cannot be taken for the one handed over (pytest).
  - **The object that waited longest goes first.** Each bin remembers where and in which turn the handed-over objects arrived, while they are still seen there; objects never handed over count as the oldest. That order comes before the grasp ranking, which then orders the grasps of one object (`grasp_selector.select`, `priority`); like the ranking, it only orders feasible candidates. Found on the development seed: without it the ranking prefers the object that was just set down, alone on the roomiest place point, and one cube made 18 of 20 handovers while four objects never moved (`phase6_relay_n2_dev_20261113T130654Z_s6000`).
  - **Memory.** Per arm, the grasps that failed; per bin, the arrivals. Both only while their object is still seen at that place.
  - **The wait for a view is counted on the simulation clock** (`PerceptionClient.wait_fresh`, the cell's too), with a wall-clock limit ten times longer in case the clock stops. With three cameras the VM simulates at half speed (`docs/environment.md`) and `perception.timeout_s` (10 s), counted in wall time, ended the first evaluation run with three arms as `no_view` after 50 handovers, all successful (E-006). A timeout in seconds of the system under test belongs to its clock.
  - **Reuse.** `BinPicking.step` does the attempt for each arm unchanged, with the place points and obstacles given from outside; `RelayLoop` adds the turn, the parking and the arrival check. All arms run on one node and share TF, joint states and the planning-scene world.
  - **Evaluation** (`scripts/relay_benchmark.py`, `scripts/relay_eval.py`): objects are spawned once, seeded, in every bin; after every turn the harness reads ground truth and re-checks the executed states of all arms with MoveIt, once per arm group: an arm against everything else, the other arms included. Checking the whole robot as one group was tried first and is wrong here: the bins are robot links, so an obstacle of the destination bin, grown by its padding next to a wall, made every state of two turns "in collision" with the bin itself (`phase6_relay_n2_dev_20261113T131850Z_s6000`, not counted). A handover succeeds only if the cell reports it, its object rests in the destination bin and no state is in collision.
- **Evidence:** pytest (`test_relay.py`, `tests/test_relay_eval.py`); E-006: with the final code 99/100 handovers with N = 2, 100/100 and 97/100 with N = 3 on two seeds, 0 of 102 189 executed states in collision, 0 undetected failures, 0 objects out of the bins; 8/8 with N = 4.
- **Limits:** throughput is that of one arm whatever N is (28 s of simulated time per turn with two and with three arms), and each turn pays two extra free-space moves (to ready and back to park). An object that an arm cannot grasp stays in its bin; when that leaves no arm with work the loop ends as `no_work`. E-006 shows how objects get there: a prism set down at a corner place point with its length towards the end wall (the place points are the cell's, D-017, chosen for a bin nobody picked from, and the loop does not choose the yaw it sets an object down at), and two objects touching after a slip, seen as one cluster. In three of the four runs of 100 handovers 2 to 4 objects had stopped going round by the end; no handover failed because of it, and how long a ring lasts was not measured.
- **Status:** accepted for phase 6.

## D-022 — Phase 7: a Rubik's cube solved by one arm, a nest and one camera

- **Context:** idea 2 of `docs/ideas.md`: an arm scrambles a Rubik's cube, another reads it with the camera and solves it. The user asked for a plan that starts simple (one or two arms and a camera, as so far) and ends with a scrambled cube physically solved, on a cube that is a faithful model of the real one and turns as it does (2026-11-13). Rule 1 forbids a cube whose state is rewritten or whose pieces are moved by a script.
- **Decision** (the user's choices among the alternatives put to them, 2026-11-13; plan approved 2026-11-14):
  - **Cube: a mechanism driven by a Gazebo system plugin**, not a pile of pieces held together by contact. A core, six axles on revolute joints and 26 cubies with their real mass, collision shape and friction; the plugin welds every cubie to the axle of its layer, so that a layer turns only when the torque applied from outside exceeds its friction and the layers across it stay locked until it is square again. The contact-only alternative (every cubie held by its neighbours, as in MuJoCo models) is closer to the real cube inside, but 26 interlocking bodies in DART on this VM were judged a high risk of never getting a cube that turns reliably. Declared idealisations: the internal interlocks are not modelled, and before another axis engages a layer that is within tolerance is pulled square and its residual angle is set to exactly zero. The mechanism itself gets its own entry once it is measured.
  - **One arm and a fixed nest**: a low square seat on a pedestal holds the bottom layer, the arm holds the two layers above it and turns its wrist; to bring another face down the arm lifts the cube, tips it over by a quarter turn and sets it down again. One overhead camera, as in the cell. Two arms holding one cube were left for later: two grippers on one object, more memory, a slower simulation.
  - **Solver: `kociemba`** (pip, GPLv2, a run-time dependency only), in a venv of its own in the VM. About 20 moves per cube; every move costs the robot about a minute of simulated time, so a solver written here with 30 to 45 moves would make every run half as long again. The install is asked for when the cell first needs it.
  - **Closing test E-007:** cubes scrambled with 25 seeded random moves, spawned in the nest in a seeded orientation. A cube counts as solved only if the cell says so, the simulator's state is solved with every layer square and the cube in the nest, and no executed state is in collision. 10 cubes on the evaluation seed (at least 9 solved), 5 on a confirmation seed (at least 4), no false `solved`; then one run in which the arm itself scrambles the cube before solving it.
- **Steps**, each ending with a runnable system and a measure: cube logic; feasibility probes of the plugin in the VM; cube mechanism on a test bench (every face turn against the logical model, locking, no drift over 400 turns); the cell with the nest; the turn (60 seeded turns); the flip (60); the scan of the six faces (20 cubes); the solve loop with verification after every operation and recovery; closing.
- **Agreed stop:** the plugin needs to know which layer the applied torque is trying to turn. Three ways to measure it are tried in the probes (the wrench transmitted by the welds, contact forces, cubies split in two links with a permanent fixed joint). If all three fail, work stops and the result is reported before any other approach is taken.
- **Evidence so far:** read-only checks of 2026-11-13. The VM has the headers and CMake configuration of gz-sim 8 and gz-physics 7.8 in the ROS vendor packages, `g++` 13 and `cmake` 3.28: a system plugin builds with nothing installed. In the gz-sim 8 sources, `Physics::Update` creates new `DetachableJoint` entities before the step and removes the old ones after it, so welds can be swapped without a step in which the cubies are free; `JointPositionReset` exists; contact messages carry the contact force. In gz-physics 7 a fixed joint attached to a link that is a free root becomes a `WeldJoint` of the tree, not a soft constraint.
- **Update 2026-11-14:** the mechanism is built and measured: D-023. A layer is not driven square before an axis change, as written above: the detent leaves a free layer within the tolerance, and only that residual is set to zero.
- **Status:** accepted; step 1 (cube logic, `openfactory_manipulation/core/rubik/`: facelet state and moves ported from the `doppelbot` project, the 26 cubies with their rotations, what a turn and a flip do to state and orientation; 226 pytest cases) done 2026-11-14.
- **Update 2026-11-14:** steps 1 to 8 done (D-023 to D-028) and the closing test passed: E-007, 10 of 10 and 5 of 5 cubes, 0 executed states in collision, 0 cubes called solved that are not, and the run in which the arm scrambles first.

## D-023 — Rubik's cube mechanism: welds per active axis, detent, change of axis on torque demand

- **Context:** D-022 chose a cube whose layers turn under applied forces, built as a mechanism driven by a Gazebo system plugin. A Rubik's cube has no fixed joint tree: a corner belongs to three layers, and which of them it turns with changes at every move. A simulator model needs one tree at a time and a rule to change it that follows the forces, not a script.
- **Decision:**
  - **Bodies** (`scripts/rubik_model.py`, `openfactory_description/config/rubik.yaml`): a core, six axles on revolute joints of the core about the face normals, 26 cubies as free links of the same model (19 mm boxes, 3 g each, friction 1.0; the cube is 57 mm and 92 g). Cubies do not collide with each other, which the welds make unnecessary; they collide with the gripper and the nest.
  - **Welds** (`RubikCubeSystem`, `openfactory_simulation/src/rubik_cube_system.cc`): one axis is active; the cubies of its two outer layers are welded to their axles, the middle slab to the core. A weld is a `DetachableJoint` entity created by the plugin, which the physics engine makes a fixed joint of the model tree: exact, no constraint to drift or to soften. Along the active axis the cube is three slabs on two revolute joints, as a real cube is while one of its layers is out of square.
  - **Turning:** the active axles are force-controlled: joint friction 0.01 N m and damping 0.003 N m s/rad from the model, plus a detent applied by the plugin, a spring of 15 N m/rad towards the nearest quarter turn capped at 0.03 N m within 8° (a magnetic cube). A layer at rest needs 0.04 N m to start; a layer that nothing holds comes to rest within 0.04° of square.
  - **Change of axis:** a cubie is a leaf of the tree, so the wrench its weld transmits is the force the outside applies to it (plus its weight, which has no moment about a layer's axis). Summed over a layer, about the layer's axis, it is the torque that would turn that layer. When it exceeds the breakaway torque (0.04 N m) on a layer of another axis, and both active layers are within 0.1° of a quarter turn, the plugin sets their angles to exactly the quarter turn, removes the 26 welds after that step and creates the new ones before the next: no step with a free cubie. If a layer moved meanwhile the old welds are put back. With an active layer out of square the other axes are rigid: the cube is locked, as the real one is.
  - **Idealised, by declaration (rule 1):** no interlocking pieces inside, so a cubie cannot be pulled out and a corner cannot be twisted in place; the exact squaring before an axis change, at most 0.1°, without which every turn would leave its residual in the welds. No pose of a cubie is ever set, by the plugin or by the harness; a cube is spawned in a state and from then on only forces act on it.
- **What was tried and dropped:** a velocity-controlled drive to square a layer before the change, and to hold the idle axles. `JointVelocityCmd` moves a bare axle but not one that carries welded links (`docs/environment.md`, "Phase 7 probes"). It was not needed: the detent already leaves the layer inside the tolerance, and the check before the welds are created catches a layer that moved.
- **Evidence:** probes of 2026-11-14 (`docs/environment.md`): weld, re-weld without a free step, transmitted wrench, exact reset. E-007 part A, on the test bench (core fixed to the world, faces turned by torques on their centre cubies): every face by a quarter turn, a half turn and a quarter turn back gives the state of the logical model, 18 of 18; 80 % of the breakaway torque turns nothing on the active axis nor on the others; with U left 30° out of square a torque of five times the breakaway on R and on F turns nothing, and R turns again once U is square; 400 seeded random turns, 326 changes of axis, every state correct, and the cubies welded to the core 7.6e-14 m from where they were spawned on the grid. The same run with the final plugin (hold during the change of axis, 25 steps of demand): the same counts, 5.3e-14 m.
- **Update 2026-11-14, after the first runs with the arm (D-024):**
  - A change of axis engages only when another axis has been asked for during 25 steps in a row: a knock (the cube landing in the nest, the fingers closing) no longer changes the axis. A sequence of 40 flips and turns had made 228 changes before.
  - The two layers that were free must stand still while the welds change, and they are loaded by the very forces that ask for the new axis (a gripper turning the cube against the nest pushes on them through the nest walls). They are now held, for those steps, by a torque equal and opposite to the one the outside applies to them, read from their welds; if a layer moves all the same, the torque that moved it is worked out from how far it went in one step, added to the hold, and the squaring is tried again, up to 50 times.
- **Update 2026-11-14, after the first evaluation run of the closing test (E-007, `p7_solve_eval_run1`): layers that rest are latched.** Two of four cubes were lost on a turn in which the cube did not turn and was dragged out of the nest. Cause: the hold above acts one step late. When the gripper starts to turn the cube and the cube binds against the nest walls, the torque jumps within a step to what the fingers can pass (about 1 N m at 20 N of squeeze), a sixth of it lands on the two layers of the axis that was free, and a layer of 15 g cm² moves 0.6° in a single step under 0.19 N m: out of square before the plugin has seen any demand, so the axis could not change and the cube stayed locked. A gentler squeeze (2.5 N) cured the turn and broke the flip (the cube then turns 4–10° between the ribs). Fixed in the mechanism instead: a layer of the active axis that is square and at rest for 20 steps is **latched**, its joint given position limits 0.2 µrad wide, and it is released only when it is the layer being turned (the torque on it about its own axis exceeds the breakaway torque and is at least what is asked of any other axis). Nothing can then push a resting layer out of square; a turn of a latched layer starts one step later. It is what the pieces of a real cube do: the layer that gives way first locks the others. Bench (`--turns 60`): all checks pass; a mixed run of 60 flips and turns with the arm (`phase7_rubik_mixed_dev_…`, the third of that name): 60 of 60, where the gentle squeeze had lost the cube at the fourteenth.
- **Limits:**
  - Measured friction, not nominal: in DART a damped joint resists more while turning than its SDF friction (1.44 times for a layer), so the numbers above are bench measurements and change with mass, damping or step.
  - A torque demand is whatever the contact solver reports. Two rigid pads that hold two layers at once are statically indeterminate, so a grasp may show a demand that no one intended and the cube may change axis while held. The change itself moves nothing; whether it disturbs the cell is measured with the robot (E-007 parts B and C).
  - Along the axis of the fingers the middle slab is held by the cube's own friction and detent only, as in a real cube held by two opposite faces.
  - Each change of axis leaks about 1.3–1.7 MB in the Gazebo server, an upstream leak of detachable joints (`docs/environment.md`): 540 MB over the 326 changes of the bench run. Long runs relaunch the simulation.
- **Status:** accepted for phase 7.
- **Update 2026-11-14, results with the latch:** every part of E-007 was run again and passes: bench 420 of 420 turns over 326 changes of axis, 60 of 60 turns and 60 of 60 flips by the arm, and 16 cubes solved of 16 (parts E and F: 359 turns, every one right at the first try). No cube was lost.

## D-024 — Rubik's cube cell: a nest on a pedestal, ribbed fingertips, turns and flips

- **Context:** D-022 chose one arm and a fixture. The arm must turn a layer and bring any face to where it can be turned, with the cell's parallel gripper and friction only (D-007), every motion planned by MoveIt (rule 4).
- **Decision:**
  - **Layout** (`rubik_cell.yaml`, `rubik_cell.urdf.xacro`, `rubik.launch.py`): the cell's table, arm, controllers and MoveIt configuration, unchanged; in place of the bins a pedestal 0.50 m in front of the base, with a square nest on top, and the cell's camera 0.70 m above the nest. `simulation.launch.py` and `move_group.launch.py` take the xacro and SRDF names as arguments whose defaults are the cell's.
  - **Nest:** a seat 58.5 mm wide (0.75 mm of play per side) with walls 8 mm high: it holds the bottom layer (19 mm) against turning and nothing else. Above each wall a rim slopes outwards (5 mm up, 4 mm out) as a lead-in, and the nest is smooth (friction 0.2): a cube set down a few millimetres off slides into its seat. The pedestal (80 mm) raises the nest so that the gripper can set the cube down with its tool horizontal: the fingers then pass 5 mm above the rim and the palm hangs beside the pedestal.
  - **One grasp** (`core/rubik/station.py`): the tool axis through the cube centre, the fingers on two opposite faces, the fingertips 2 mm above the top of the bottom layer when the tool points down.
  - **Ribbed fingertips** (`rubik_gripper.yaml`: the cell's gripper plus `finger.pad`): three ribs 3 × 15 mm standing 2 mm out of the fingers at their tips, two on the left finger 11 mm apart and one on the right finger between them. Nothing else of the gripper touches the cube. All three bear on the centre cubie of a face, at the height of the cube centre.
  - **Turn** (`CubeHandler.turn(k)`): grasp from above, the wrist turns k quarter turns about the vertical (a Cartesian path through poses 30° apart), release. The ribs hold the middle layer by the centres of two faces, the nest holds the bottom layer: the bottom layer turns against the rest, and the top layer follows the middle one.
  - **Flip** (`CubeHandler.flip(kind, yaw)`): grasp, lift 50 mm, turn the held cube `yaw` quarter turns about the vertical, tip it a quarter turn about the finger axis (an arc through its centre), lower it to 1.5 mm above its seat with the tool horizontal, let go, back off 60 mm along the tool axis, rise 100 mm, back to ready. Two kinds were found reachable with MoveIt's collision-aware IK: `over` (the arm reaches over the nest and the tool ends pointing back at the robot; the face that looked away comes down) and `side` (the tool ends along +y). Pointing away from the robot is not reachable with the pedestal at 0.50 m. With the yaw any of the four side faces comes down in one flip, the top face in two.
  - **Planning scene:** the cube is two boxes 1 mm smaller per side than the real ones, the bottom layer and the two layers above it. For a turn only the upper box is attached to the gripper, for a flip both.
  - **Recovery** (`_recover_cube`): a seated cube stays in the planning scene so that the way back goes round it; a cube held with the tool still down is set down again; otherwise it is let go and taken out of the scene, and the next view has to say where it is.
- **What was found on the way** (all in the simulator, ground truth read by probes):
  - *A flat pad cannot carry the cube through a flip.* With the cell's fingers as pads, the cube turned 17–22° between them as soon as the tool tilted, and slid 5 mm towards the fingertips; the jaw opening did not change. DART's default contact solver (Dantzig) returns a basic solution: the whole squeeze on one contact point per pad, which carries no torque about the finger axis (the finding of D-015, now on a box). The projected Gauss-Seidel solver spreads the force and held the cube within 0.4°, but it is iterative: joints that should stand still creep, the cube mechanism could no longer change axis reliably under load, and the grip on a turn was soft. Kept: Dantzig. Fixed in the geometry: three ribs make the grasp statically determinate (the two left ribs share the squeeze whatever the solver does), and their 11 mm are the lever that turns the cube with the gripper. With the ribs the cube stays within 0.07 mm and 0.2° of the gripper through both kinds of flip.
  - *Pads wider than a cubie twist the layers beside it.* The fingers are 20 mm wide, a cubie 19 mm: half a millimetre of pad on the neighbouring slabs was enough to turn them out of square. The ribs span 14 mm.
  - *Pads above the centre of a face spin that face.* With the pads on the two upper rows, the friction that turns the cube about the vertical acts 10 mm above the axis of the face it presses on, and turns that face layer as well. The ribs are at the height of the cube centre: what turns the cube passes through the axis of the face.
  - *The squeeze moves the cube off the tool axis by the squeeze depth* (the mimic finger yields, D-010): 0.3 mm here, where the nest leaves 0.75 mm.
- **Evidence:** development run `phase7_rubik_mixed_dev_…_s7100` (2026-11-14): 40 of 40 flips and turns in a seeded mixed sequence left the simulator's cube in the state and orientation the logical model predicts, seated within 1.0 mm and square within 0.02 mm; 0 of 6519 executed states in collision; mean 16.5 s of wall time per operation. E-007 parts B and C for the test runs.
- **Limits:** the cube must start in the nest; nothing picks it up from elsewhere. A cube that ends on the rim or off the pedestal is lost (`cube_lost`). Top-down access only: the top face needs two flips.
- **Status:** accepted for phase 7.

## D-025 — Perception of the cube: pose and squareness from depth, sticker colours from the image

- **Context:** the cell must know, from the camera only (rule 5), that the cube stands in its seat with every layer square before it grasps it, and what the face that is up shows. Rule 3 asks for a geometric baseline first; colour had been used for debug views only (D-011).
- **Decision** (`openfactory_perception/core/cube_view.py`, node `cube_perception`):
  - Depth → points in the nest frame → points within 6 mm of the cube-top height: the top face. Fewer than 600 of them: no cube stands in the nest. Smallest rectangle around them: centre, yaw within ±45°, sides; plane through them: tilt and roughness.
  - Points lower than the top face and outside its outline (3 mm margin), above the rim of the nest: the area a lower layer shows when it is out of square.
  - The nine sticker centres of the top face are projected into the colour image (same optical centre); each sticker is the median colour of a patch 0.4 cubies wide.
  - Output: `/perception/cube/detection` (`vision_msgs/Detection3DArray`, world frame, image stamp): empty, or one detection of class `rubik_cube` with the cube pose (orientation of the top face), the measured sides and height, and a score exp(−½ Σ residual²) over the protruding area, the roughness and the two sides, which falls when the cube is not a square block. `/perception/cube/top_face` (`sensor_msgs/Image`, 3 × 3 `rgb8`): the sticker colours as seen from above, same stamp. What the colours mean is decided by the consumer, which sees six faces (D-026).
- **Evidence:** 32 pytest cases on synthetic views (z-buffered cube, rim, depth model): pose within 1.2 mm and 1.5°, colours exact, a layer 12° out of square shows 0.6 cm² or more, a square cube under 0.3 cm². Live, 2026-11-14: cube centre within 0.2 mm of its seat, sides 57.9 and 58.0 mm, score 0.89; rendered sticker colours are the model's times 1.1, flat (white 255, red 224 0 0, orange 255 112 0, yellow 255 238 0, green 0 168 42, blue 0 56 224), far apart. First scan of a development cube: state and orientation equal to the simulator's.
- **Finding:** stickers 0.4 mm proud of the black body went missing in the image now and then, one or two per view: the renderer's depth buffer cannot tell them from the body under them. At 0.8 mm and 1.0 mm none was missing in eight views; the model uses 1.0 mm (visual only).
- **Limits:** one face per view. A layer less than about 8° out of square does not show (the detent of the cube pulls it square from there, D-023). The colours are those of a simulator with flat shading: no shadows, no highlights.
- **Status:** accepted for phase 7.

## D-026 — Reading the cube and planning the solution: six views, then flips that bring a face down

- **Context:** the cell does not know how the cube sits at the start. It can see one face at a time and turn only the face that is down.
- **Decision** (ROS-free, `openfactory_manipulation/core/rubik/`):
  - **Scan** (`scan.py`): look at the face that is up, flip, look again, until six faces have been seen. The flips are the cheapest sequence that shows every face whatever the start (`plan.scan_plan`, a search over orientation and faces seen: five flips). For every view the cell knows only how it has turned the cube since the first one. The six centre colours are matched as a whole to the colours of the cube model (fixed infrastructure): that names the faces, and with the turns made it fixes the orientation at the start, the only one of 24 that agrees with all six views. Every other sticker takes the letter of the centre it is closest to in RGB, nine per letter at most. The result must be a state a cube can be in (`cube.check_solvable`); if not, the scan is repeated.
  - **Plan** (`plan.py`): a solution is a list of face turns (`kociemba`, D-022); the cell makes a move by bringing its face down and turning the gripper the other way. Dynamic programming over the four orientations that have the face down, with the cheapest flips between orientations precomputed over the 24: fewest seconds of flips for the whole solution.
  - **Belief:** the cell keeps the state and the orientation it believes, updated by the logical model after every operation (`orientation.py`, `plan.apply`).
- **Evidence:** 47 pytest cases: the scan plan shows six faces from each of the 24 orientations; eight scrambled cubes in random orientations read back exactly from darkened, noisy colours; a view attributed to a flip that did not happen, or two stickers swapped, is rejected; plans of 20 random moves make exactly those moves with at most 1.6 flips per move.
- **Status:** accepted for phase 7.

## D-027 — Solve loop: every operation verified by the next view, a mismatch means scan again

- **Context:** the cell must detect its own failures (the cube out of its seat, a layer left out of square, a turn that did not happen) and never call a cube solved that is not.
- **Decision** (`openfactory_manipulation/rubik.py`, `RubikSolver`):
  - After every flip and turn the arm goes to ready and the cell takes a view. The view must show a cube seated (centre within 2 mm, tilt and yaw within limits) and square (score ≥ 0.5): otherwise the loop ends as `cube_lost` or `not_square`, except for a cube standing in its seat with its top turned about the vertical, which is turned back (`CubeHandler.realign`).
  - Once the state is known, the nine stickers of the view, read against the six centre colours seen in the scan, must be the face the believed state has up. If the cell reported a failure and the view shows the face that was up before, nothing moved and the operation is tried again (twice at most). Any other disagreement abandons the plan: scan again, solve from what is there.
  - The cell reports `solved` only after a scan of the six faces that reads the solved state: the last one is always made, after the solution has been executed.
  - End reasons: `solved`, `scan_failed`, `cube_lost`, `not_square`, `no_view`, `failure_budget`, `operation_budget`, `solver_failed`.
- **Evaluation** (`scripts/rubik_benchmark.py`, `scripts/rubik_eval.py`): one cube per launch of the cell (the Gazebo server leaks memory at every change of axis, `docs/environment.md`); ground truth after every operation; a cube succeeds only if the cell says `solved`, the simulator's cube is solved, square and seated, and no executed state is in collision. Contacts of the fingers with the cube are the task and are not collisions; anything else is.
- **Status:** accepted for phase 7; closing test not run yet (the solver is not installed).
- **Update 2026-11-14:** the solver is installed (D-028) and the closing test passed (E-007, parts E and F: 16 cubes solved of 16, no operation misjudged by the cell). Nothing failed in it, so the two recoveries of this loop that need a fault, `realign` and the scan again after a mismatch, have never run on a cube and have no test: `docs/experiments.md`, E-007, conclusion; `docs/ideas.md`, idea 2.

## D-028 — Solver dependency: `kociemba` from pip, in a venv of its own

- **Context:** D-022 chose `kociemba` for the solution. It is not an apt package; Ubuntu 24.04 refuses `pip install` into the system Python; the `doppelbot` project on the same VM keeps its copy in a venv that is activated for every build, which once broke entry points built with the system `colcon` (`docs/environment.md`).
- **Decision:** a venv used only as a place for the library, `~/openfactory_ws/.venv_solver`, filled from the pinned `requirements-vm.txt` at the repo root (`kociemba` 1.2.1, `cffi` 2.1.1, `future` 1.0.0, `pycparser` 3.11). It is never activated: the processes that solve get its site-packages on `PYTHONPATH` (`scripts/vm/run_rubik.sh` reads the path from `~/openfactory_ws/solver_path`). The library is imported in one place, inside `core/rubik/solver.solve`; `openfactory_manipulation` gains no dependency in `package.xml`, and its tests skip the solver test when the library is not there. `RubikSolver` takes the solver as an argument, so another one can stand in.
- **Licence:** `kociemba` is GPLv2. It is not copied into the repository nor linked into anything the repository ships; it is called at run time.
- **Evidence:** installed 2026-11-14 with the user's approval (`docs/environment.md`); solver test passes; development cube solved with a 21-move solution (`p7_solve_devkoc`, E-007), then with the library read from the `doppelbot` venv, same version.
- **Status:** accepted for phase 7.

## D-029 — Videos: a film camera created in the running world, recorded by Gazebo on simulated time

- **Context:** every element of the project should have a video of a real run, the Rubik's cube cell and the ring first. The VM runs the ring at 0.2–0.5 of real time. The Gazebo window costs about 400 MB, ended once with a segmentation fault with the ring (`docs/environment.md`, "Phase 6 ring") and on 2026-11-14 a demonstration with the window lost a cube when Gazebo stopped answering (cause not found: the log of that launch was overwritten).
- **Decision:**
  - A take films one real run, without the window. `scripts/film.py` launches the system, creates a **film camera** in the running world, starts the recording, runs the scenario of the take (a benchmark harness, so the run is judged from ground truth), stops the recording and the system. Takes are entries of `scripts/config/film.yaml`: launch, shot (position and the point looked at, world frame), scenario, parameters.
  - The film camera is a Gazebo model of its own (`film_shots.camera_sdf`): static, no visual, no collision, one `camera` sensor, spawned and removed through the world's `create` and `remove` services like any harness object. No launch file, xacro or package changes, so the cell, the ring and the Rubik's cube cell are what they were. It is not bridged to ROS: nothing in perception or manipulation can read it (rules 2 and 5).
  - The sensor carries Gazebo's `CameraVideoRecorder` system (`gz-sim-camera-video-recorder-system`, part of `ros-jazzy-ros-gz`) with `use_sim_time`: frames are stamped with simulated time, so the video plays at the speed of the simulated system however slowly the VM ran it. H.264 in mp4, encoded by the Gazebo server (libx264 through `gz-common`).
  - Editing happens on the Mac with ffmpeg (`scripts/film_edit.py`): copy, speed up, cut, GIF. The recording is never changed; an edit is a new file with its speed in its name.
  - Every take writes `take.json` next to the video: git commit, parameters (seed set, index), shot, simulated times, exit codes of the scenario (rule 6). A take whose scenario fails is recorded as failed and keeps its video.
- **Alternatives:** the GUI's `VideoRecorder` (`/gui/record_video`, with `lockstep`) needs the window; a screen capture of the VM desktop records wall time and the window; a camera in the fixtures xacro behind a launch argument would change the description of three systems for something that is not part of them.
- **Evidence** (probe 2026-11-14, `docs/environment.md`, "Filming"): the plugin loads on a sensor of a model spawned at run time; 7.0 s of simulated time recorded in 27 s of wall time gave a file of 7.07 s, 1280×720, H.264, 15 frames per second; the render is lit and shaded (Ogre 1, no shadows).
- **Limits:**
  - The film camera slows the simulation: real-time factor 1.0 → about 0.3 at 1280×720 and about 0.65 at 960×540 in the Rubik's cube cell; the frame rate (10 or 15) makes no difference. A take therefore lasts about three times its simulated time.
  - One fixed shot per take. More cameras are more renders.
  - The ffmpeg of the Mac (9.0.1 from Homebrew) has neither `drawtext` nor `subtitles`: no caption or speed label is burned into an edit.
- **Status:** accepted.
- **Update 2026-11-14:** first takes made, one of the Rubik's cube cell and one of the ring of three arms, both runs passed by their harness (`docs/experiments.md`, "Filmed runs"). The scenario of a take must be a full set of its benchmark: a shortened run exits 1 by design and the take is then recorded as failed.
- **Update 2026-11-15, orbit shots:** a shot may carry `orbit: {duration_s, revolutions}`: the camera starts where the shot stands and goes round the vertical through the point it looks at, at the same height and distance, `revolutions` times (default 1) in `duration_s` of simulated time, the time the take is expected to last.
  - How: the sensor sits on a link that a revolute joint to `world` turns about that vertical, and Gazebo's `JointController` system (`gz-sim-joint-controller-system`, part of `ros-jazzy-ros-gz`) holds the joint at a constant velocity. The camera moves in the physics step, so every frame is rendered from where the camera is at that simulated time: the motion is even in the video whatever the real-time factor. The link has no collision, no visual and no gravity. Moving a static camera with `set_pose` calls from the harness was not tried: the pose would follow the wall clock of the script, not the frames.
  - The length of a run is not known before it ends, so `duration_s` is an estimate (the same take filmed before) and `take.json` records the revolutions actually made (`orbit_revolutions`).
  - The world has one directional light and no shadows: from the side away from the light the arm is seen in its unlit side. No light is added for the film, because it would change what the cell's own camera sees.
  - `film.py take --fixed` leaves the orbit out; `film.py still --angle DEG` shows the view from a point of the orbit.
